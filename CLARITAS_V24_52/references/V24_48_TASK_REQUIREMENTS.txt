======================================================================
FIX 1 — CUDA STATE ARRAY MEMORY LAYOUT
======================================================================

The V24.47 129-state regression constructs the state array approximately as:

    states = rf[['x','y','z','vx','vy','vz']].to_numpy(np.float32)

The resulting NumPy object can be Fortran-contiguous rather than C-contiguous.

The CUDA kernel accesses the buffer as rows:

    const float* q = states + 6*id;

which assumes C-contiguous row-major [N,6] storage.

CuPy can preserve the source memory layout when transferring the NumPy array, meaning the kernel can read scrambled state vectors.

Correct this robustly.

At minimum, the host-side state input should use an explicit contiguous representation equivalent to:

    states = np.ascontiguousarray(
        rf[['x','y','z','vx','vy','vz']].to_numpy(dtype=np.float32)
    )

However, do NOT fix only this one call site.

Audit EVERY NumPy/CuPy host array passed to raw CUDA kernels in the V24.48 qualification/geometry validation path.

For arrays whose CUDA indexing assumes C-order:

- explicitly require C-contiguous storage;
- assert expected dtype;
- assert expected dimensions/shape;
- preferably assert strides or contiguity immediately before launch;
- fail loudly if an invalid layout reaches the launch boundary.

Do not depend on NumPy/Pandas/CuPy implementation accidents.

Add a regression test that deliberately creates an F-contiguous [N,6] input and verifies that the validation infrastructure either:
1. safely converts it to the required layout, or
2. rejects it before kernel execution.

The test must demonstrate that this exact V24.47 failure mechanism cannot recur.

- just inside tolerance;

FIX 3 — FULL-PATH WATCHDOG/CAP COMPARISON LOGIC
======================================================================

Audit the full-path opportunity validation.

The V24.47 Python reference can validly return something equivalent to:

    (-2, 8192)

when no non-TIR opportunity is found before its validation execution cap.

The V24.47 mismatch comparison nevertheless appears to contain logic equivalent to:

    pmis += int(
        int(pst[i]) != 1
        or int(pos[i]) != es
        or int(pic[i]) != ei
    )

This automatically marks a CUDA trajectory as wrong whenever the CUDA status is not 1, EVEN WHEN BOTH CUDA AND REFERENCE CORRECTLY REACH THE SAME VALIDATION CAP.

Correct the comparison semantics.

A watchdog/cap result must be compared as a watchdog/cap result, not against the successful-opportunity status.

Define explicit comparable terminal-state categories such as:

- physical opportunity found;
- escaped/terminated physically;
- watchdog/progress termination;
- emergency execution cap;
- invalid numerical state/error.

The exact categories should reflect the actual code rather than forcing this suggested naming.

CUDA and reference should agree on:

- physical terminal class;
- relevant interface/opportunity index where applicable;
- interaction count where applicable;
- watchdog/cap semantics.

Do NOT reinterpret a watchdog/cap trajectory as successful physics.

It simply must not be called a CUDA/reference mismatch when both implementations have reached the same defined nonphysical validation termination condition.

V24.47 analysis indicated that roughly 176 of the 4096 reference paths reach the reference's own 8192 cap, meaning most of the headline 184 mismatches may be caused directly by this comparison bug.

Verify this independently from the supplied files.

Do not hard-code the number 176 into the validator.
