4. PRIMARY FUNCTION TO AUDIT: smith_beckmann_lambda
======================================================================

Inspect the actual V24.40 implementation.

Look for a Smith Beckmann Lambda calculation equivalent to:

    float lam =
        0.5f * (erff(a) - 1.0f)
        +
        (INV_2_SQRT_PI / a) * expf(-a*a);

or mathematically equivalent code.

For positive a, the true Beckmann Smith Lambda should be non-negative.

However this expression is numerically dangerous for moderately large positive a because it subtracts two very small, nearly equal quantities.

The terms:

    0.5 * (erf(a) - 1)

and:

    exp(-a^2) / (2 sqrt(pi) a)

can be individually much larger than their final difference.

In float32 the result can therefore become:

    slightly negative
    zero when it should be positive
    badly inaccurate

even for physically ordinary directions.

If V24.40 then performs logic equivalent to:

    if (!isfinite(lam) || lam < 0)
        numerical_failure;

then a floating-point cancellation error becomes:

    HEIGHT_CDF_INVALID

even though the physical state is valid.

YOU MUST VERIFY THIS AGAINST THE ACTUAL SOURCE.

Do not blindly replace code based only on this prompt.

Confirm the coordinate convention, alpha scaling, definition of a, and sign conventions.

8. SECOND PRIMARY TARGET: smith_sample_height
======================================================================

Inspect the complete V24.40 Smith height/free-path sampler.

The current mathematical structure may contain operations equivalent to:

    G1 = powf(C1, lambda);

    if (U > 1 - G1)
        ESCAPE;

    denom = powf(1 - U, 1 / lambda);

    Cnext = C0 / denom;

This is mathematically valid in exact arithmetic but can be badly conditioned.

Problems include:

    G1 ~= 1

so:

    1 - G1

loses precision.

Also:

    lambda -> 0+

causes:

    1 / lambda

to become very large.

The escape test and Cnext calculation can then be evaluated through separately rounded pow() operations that disagree near the transition boundary.

That can result in:

    Cnext > 1

or another apparently invalid CDF state even though the exact physical expression is valid.

V24.40 then correctly labels this as a numerical failure.

V24.41 must prevent the numerical instability rather than hiding it.
